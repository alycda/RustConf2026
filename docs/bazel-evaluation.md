# Would Bazel improve this repo?

Short answer, unchanged from the first pass: **not for the repo as it exists**,
and not for anything an attendee touches. What changed is the second half of
the question — *"if I solve every Advent of Code day and implement FFI in at
least one direction"* — where the answer becomes a qualified yes, for a
specific person (the maintainer), in a specific place (CI), under conditions
this document tries to state precisely.

Everything below was built and measured, not estimated, unless a line says
otherwise. The overlay is in this branch: `MODULE.bazel`, `.bazelrc`,
`tools/aoc.bzl`, `tools/gen_day_build.py`, generated `days/*/BUILD.bazel`,
and `bazel/ffi_smoke/`. `just`, `cargo` and `shell.nix` are untouched.

## What actually got built

Bazel 9.2.0, `rules_rust` 0.74.0, a `1.85.0` Rust toolchain pinned to the
floor `days/Cargo.toml` declares. 71 targets, 12 test targets, all green:

```
bazel test //...
```

Both FFI directions work.

**Export — Rust to C, the Exercise 2 chain.** For a day with `src/c_api.rs`
and `cbindgen.toml`, `aoc_day()` produces `:lib`, `:test`, `:bin`, `:cdylib`,
`:header` (cbindgen output) and `:c_api` (a `cc_library` carrying the header
and the shared object). `//bazel/ffi_smoke:day_2015_12_06` is a `cc_test`
that calls `aoc_2015_12_06_part1` and gets 998996 back. Its entire link
configuration is `deps = ["//days/2015-12-06:c_api"]` — no `-L`, no `-rpath`,
no `dlopen`, no debug-then-release search.

**Import — C into Rust.** `//days/2024-12-01:test_cfeatures` builds the day
with `qsort` and `cpp` on and runs 9 tests, the same 9 that
`cargo test -p aoc-2024-12-01 --features qsort,cpp` runs, including the ones
asserting the C answer equals the pure-Rust one. The C++ side does *not* go
through `build.rs` and the `cc` crate: it is a `cc_library` on Bazel's own
toolchain, wired in through `link_deps`. That is strictly less machinery than
the cargo path.

**cbindgen is a build target, not a prerequisite.** `crate.from_specs` builds
cbindgen 0.29.4 from source. This is the one unambiguous improvement in the
whole overlay: `scripts/self-check.sh` exists in large part to police
cbindgen's presence and version floor, and under Bazel that check cannot fail
because there is nothing to install.

## Measurements

Nine days plus `_template`, 12 Bazel test targets, on this container. `cargo`
column is `cargo test --workspace --locked`; `bazel` column is
`bazel test //days/... //bazel/...`.

### Full build

| | cargo | bazel |
|---|---|---|
| cold (`rm -rf days/target` / `bazel clean`) | **26.7s** | **190.5s** (934 actions) |
| fully warm, nothing changed | **0.6s** | **1.3s** |

Bazel's cold number includes compiling cbindgen and its dependency tree from
source. That is a one-time cost per cache, not per build, but CI pays it on
every cold runner unless a remote cache is in front of it.

### One edit, measured with a `black_box` inserted into a live function body

| edit | cargo | bazel |
|---|---|---|
| A. pure-Rust day (`2020-12-02`) | 0.9s — 1 crate recompiled, **20 test binaries run** | 1.4s — 7 actions, **1 of 11 tests re-run** |
| B. FFI day, solution logic (`2015-12-06/src/lib.rs`) | 0.9s — 1 crate, **20 test binaries** | 1.7s — 12 actions, **2 of 11** |
| C. FFI day, C surface only (`2015-12-06/src/c_api.rs`) | 0.9s — 1 crate, **20 test binaries** | 1.5s — 13 actions, **2 of 11** |
| D. a day nothing binds to (`2022-12-01`) | 0.8s — 1 crate, **20 test binaries** | 1.3s — 7 actions, **1 of 11** |

The shape is the whole argument, and it is not "Bazel is faster" — at this
size Bazel loses every row on wall clock. It is this: **cargo recompiles
precisely and then re-runs everything; Bazel does both precisely.** Row D is
the clean case — a change to a day nothing binds to costs Bazel exactly one
test and costs cargo the entire workspace's test suite.

At nine days that distinction is worth nothing, because 20 pure-Rust test
binaries with tiny suites cost about 0.3s in total. Which is why the honest
verdict for the repo as it stands is still no.

### Reverse-dependency selectivity

```
bazel query 'rdeps(//..., //days/2015-12-06:cdylib)'
  //bazel/ffi_smoke:day_2015_12_06
  //days/2015-12-06:c_api
  //days/2015-12-06:cdylib
```

That first line is the edge `just` cannot express. In `days/justfile` the
relationship is a recipe dependency — `swift-demo day: (bindgen day)` — which
*re-runs* cbindgen unconditionally. Here it is a file dependency: the header
is an output with a declared consumer, so the C harness rebuilds if and only
if the generated bytes changed. Row C above is that working — editing
`c_api.rs` reaches the C harness; editing an unrelated day (row D) does not.

Bazel also prunes by output digest, which is sharper than expected: appending
a comment to `lib.rs` recompiles the rlib and then stops, because the rlib is
byte-identical. Adding an *unreferenced* `pub fn` likewise costs nothing
downstream — rustc drops it, the test binary digest is unchanged, and the test
is not re-run. Both of these initially looked like a broken measurement.

## Seven things that bit, in order of how much they would cost you

**1. `crate_universe` rewrites `days/Cargo.lock`.** Measured: +181 lines —
cbindgen, clap, anstream, toml\_edit, tempfile, and a synthetic
`direct-cargo-bazel-deps` package. This is not cosmetic for this repo.
`days/Cargo.toml` says in its own comments that the committed lockfile is what
stops a bonus dependency from raising the rustc floor, and rust.yml's `msrv`
job tests that exact committed resolution under 1.85. A lockfile Bazel
rewrites behind cargo's back means `cargo test --workspace --locked` — the
gate in `days/justfile` and in three CI jobs — fails after any `bazel build`.

Bisected: the `from_cargo` tag alone leaves the lockfile byte-identical. The
pollution comes entirely from the `from_specs` tag that builds cbindgen, and
giving that tag its own `cargo_lockfile` does **not** fix it — one extension
instance splices one root workspace. The fix that works is a separate
extension instance via `use_extension(..., isolate = True)`, which requires
`--experimental_isolated_extension_usages` in `.bazelrc`. Keeping the repo's
MSRV guarantee intact therefore depends on a flag Bazel still calls
experimental. `skip_cargo_lockfile_overwrite = True` is not an alternative:
it makes crate\_universe run `cargo metadata --locked` against a spliced temp
workspace it is no longer allowed to write, which fails outright.

**2. `crate_features` does not propagate through `rust_test(crate = ...)`.**
Set it on the library, omit it on the test, and the target still passes —
with 5 tests instead of 9. The `#[cfg(feature = "…")]` test modules silently
vanish. A green build with quietly reduced coverage is the worst failure mode
a migration can have, and nothing warns.

**3. Proc macros that read the manifest need it declared.** Every `#[rstest]`
in the repo fails with ``Could not find `Cargo.toml` in manifest dir`` until
`compile_data = ["Cargo.toml"]` is on the test target. Under cargo the whole
source tree is readable, so this class of undeclared read is invisible; the
sandbox is what surfaces it. Expect more of these as days acquire
dependencies.

**4. `build.rs` works — but only while the feature gates are off.**
`cargo_build_script` handles all five build scripts here, because with no
features enabled they probe nothing and emit only `rerun-if-changed` lines.
Turn a gate on and the model diverges hard: `pkg-config` inside the sandbox
is an undeclared read of an undeclared binary against an undeclared
`PKG_CONFIG_PATH`. Cargo's answer is "be inside nix-shell". Bazel's answer is
a `cc_library` per library, and **the eight libraries behind those gates are
caca, tcc, hyperscan, ICU, chipmunk, duckdb, yara and espeak-ng.** Building
duckdb, hyperscan and ICU under Bazel is a serious project on its own. This
is the wall, and `tools/gen_day_build.py`'s `SELF_CONTAINED` table stops
exactly here — `qsort` and `cpp` are in it; `uthash` is not, because its
header is a nix package.

`rules_nixpkgs` bridges this, at the cost of a third build system in the
dependency chain and of the hermeticity that justified Bazel in the first
place.

**5. `CARGO_MANIFEST_DIR` means something else.** Every day's `main.rs`
resolves `inputs/<day>.txt` through it. Under Bazel that is an execroot path,
so the input has to arrive as a runfile — `data = ["//inputs:day_inputs"]`.
Harmless here, but it is the general shape of the problem: anything locating
a file relative to the source tree needs re-expressing.

**6. `members = ["*"]` survives, which is the good news.** I assumed
MODULE.bazel would need one `manifests` entry per day and that 275 days meant
275 hand-maintained lines. It does not: crate\_universe resolves the glob
through cargo itself and says so if you list the members — *"Only the
workspace's Cargo.toml is required in the `manifests` attribute"*. So a new
`just days new` day needs no MODULE.bazel edit, exactly as it needs no
`Cargo.toml` edit. The per-day `BUILD.bazel` still has to exist, which is what
`tools/gen_day_build.py` is for; run it with `--check` in CI and a
hand-edited generated file fails the build.

**7. `_template` is a workspace member.** `members = ["*"]` sweeps it in, its
crate is `aoc-day-template`, and `aoc_day()` needs an explicit `crate_name`
to skip the `YYYY-MM-DD` check for it. Same wrinkle the `exclude` list in
`days/Cargo.toml` exists to manage, in a new place.

## Scaling to 275 days with FFI in one direction

What does **not** change: the cold-build gap, the per-edit wall clock at the
scale of a single day, and the fact that attendees should never type `bazel`.

What does change is one number. `cargo test --workspace` re-runs every test
binary in the workspace on every invocation. Today that is 20 binaries of pure
Rust and costs about 0.3s. At 275 days where each day has FFI in at least one
direction, "every test binary" includes every foreign-language harness, and
those are not pure Rust: the Kotlin track pays JVM startup per run, the Dart
track pays `dart pub get` and VM startup, the Swift track pays a `swiftc`
compile, and the Python track pays interpreter startup plus a `cffi` cdef
parse. Bazel re-runs only the harnesses whose inputs changed, and by row D
above, editing one day reaches exactly one day's harnesses.

**I did not measure the per-invocation cost of the Kotlin, Dart or Swift
harnesses** — this container has no `kotlinc`, `dart` or `swiftc`, so I could
only build and run the C track. That per-invocation cost is the variable the
whole thing turns on, and it is the number to measure before committing to
any of this. Multiply it by 275 and compare against Bazel's cold-build
overhead plus the seven items above. If a foreign-language harness costs a
second, "re-run everything" is 275 seconds of CI per push and Bazel's
selectivity pays for itself quickly. If the harnesses can be batched so one
JVM or one interpreter serves all 275 days, most of the advantage evaporates
and `just` plus a smarter runner is the cheaper answer.

The other thing that changes at 275 days is `.github/workflows/env-check.yml`.
It is already 765 lines, and its structure is an explicit step per day per
track — `python track end-to-end (2015-12-01)`, `dart track end-to-end
(2015-12-05)`, and so on. That does not survive multiplication by 30. Whatever
replaces it needs a dependency graph or a generator; Bazel is one answer,
`bazel query` giving CI the affected-target set is the specific mechanism, and
a generated matrix from `tools/gen_day_build.py`-style metadata is a cheaper
one that keeps `just`.

## What I did not verify

- The nix/`pkg-config` days under Bazel with features enabled. No nix in this
  container, and item 4 above is why this is not a small gap.
- Kotlin, Dart and Swift tracks under `rules_kotlin` / `rules_dart` /
  `rules_swift`. `dart-lang/rules_dart` is archived and the surviving
  community fork describes itself as infrequently maintained, so the Dart
  track has no supported Bazel path at all today.
- macOS. Everything here is Linux `x86_64`, and the workshop's whole subject
  is linking on the platform where attendees are.
- Remote caching, which is where most of Bazel's CI argument actually lives.

## Recommendation

If you do this, do it as **two interfaces over one graph**: `just` stays the
five-tool attendee contract exactly as the README promises, and Bazel becomes
the maintainer's tool for "did I break any of 275 days across six tracks."
Nothing in the overlay on this branch touches the attendee path, and that is
deliberate — the raw `swiftc -Xlinker -rpath` line in `days/justfile`, with
its twenty lines of comment on why `-L` does not imply `-rpath`, *is* the
workshop. Bazel's job is to hide precisely that, and a `cc_test` whose entire
link configuration is `deps = [":c_api"]` teaches nobody anything about FFI.

Do it only after measuring the foreign-language per-invocation cost, and only
if you are willing to own item 1 (an experimental flag standing between you
and a corrupted lockfile) and item 4 (eight C libraries, or `rules_nixpkgs`,
or permanently reduced coverage under Bazel relative to `just`).

The cheaper thing to try first, and the one that fits the investment you have
already made: a flake with per-day derivations. It gives content-addressed
caching and a real dependency graph, it keeps one hermeticity story instead of
two, and it does not require a second build system to learn a language
Bazel has no maintained rules for.
